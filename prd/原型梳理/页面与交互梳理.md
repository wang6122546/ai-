# 安全作业管理原型页面与交互梳理

检查对象：

- `安全作业改造.zip`：桌面端安全作业管理原型（React + TypeScript + Vite）
- `App作业管理.zip`：移动端作业管理原型（React + TypeScript + Vite）

检查日期：2026-08-18

## 一、检查结论

两个压缩包均已解压、安装依赖、构建并实际启动检查。App 端构建正常；桌面端导出包的 `src/styles/theme.css` 存在一个多余的右花括号，导致 Tailwind 构建失败，已仅修复该括号问题，未改变设计和业务内容，修复后可正常构建与运行。

原型为纯前端演示，所有业务数据均来自 `App.tsx` 内的静态数组，没有后端接口、数据库、登录鉴权或持久化能力。

## 四、核心交互流程

### 桌面端主流程

`作业监控/作业概览 → 分类 → 作业类型列表 → 查看详情`

`作业类型列表 → 申请作业票 → 填写信息 → 提交流程节点`

`隐患排查 → 状态/风险筛选 → 隐患记录`

`智能监测 → 点位状态/报警 → 趋势分析`

`参数配置 → 配置页签 → 业务开关或基础字典`

### App 端主流程

`首页 → 最近作业/综合作业列表 → 综合详情 → 审批或提交`

`首页 → 待办模块 → 待办列表`

`首页 → 作业类型 → 分类作业列表 → 分类详情 → 监护报告`

`分类作业列表 → 申请作业票 → 返回分类列表`

## 五、数据结构梳理

### 桌面端 WorkRecord

```ts
{
  id, type, cat, unit, area,
  applicant, responsible,
  startDate, endDate, applyDate,
  status: "申请中" | "作业中" | "已完成" | "作废",
  risk: "高" | "中" | "低",
  ticketNo
}
```

主要关联关系：

- `cat` 将记录归入 regular、hazardous、major、cross。
- `type` 对应具体作业类型。
- `ticketNo` 是列表和详情应使用的业务标识。
- 状态和风险同时驱动筛选、数量统计和颜色样式。

其他桌面端模型：

- `HazardRecord`：隐患类型、描述、区域、上报/责任人、风险、状态、期限、日期。
- `MonitorPoint`：设备点位、类型、区域、值、单位、阈值、状态、更新时间。
- `Survey` → `Question[]`：自定义表单及题目结构。
- 图表数据、报警数据、参数配置均为独立静态数组，未与作业记录建立强关联。

### App 端 WorkOrder

```ts
{
  id, title, type,
  typeColor, typeBg,
  level, levelColor, levelBg,
  startTime, endTime, location,
  leader, guardian, guardianExtra?,
  progressLabel,
  status: "待审批" | "进行中" | "已完成" | "已关闭",
  progress,
  actionLabel
}
```

主要关联关系：

- 首页最近作业、综合列表和综合详情共用 `workOrders`。
- 分类作业列表另用 `WorkTypeOrder` 和独立的演示详情数据，与 `WorkOrder` 不是同一数据源。
- `todoItems`、`workTypes`、施工项目、关联票证、监控设备、安全措施均为独立静态数组。

## 六、原型问题与实现风险

1. 桌面端详情数据与列表选择不一致：从“常规作业”查看后，详情显示固定的动火作业示例。
2. 桌面端“我的待办”没有内容组件；自定义表单组件没有导航入口。
3. App 的综合作业详情与分类作业详情是两套重复组件和两套数据，后续开发容易产生字段、状态和交互不一致。
4. App 底部“扫码／消息／我的”未实现页面。
5. 多处按钮只有视觉效果，缺少提交结果、校验、成功/失败反馈、确认弹窗和异常状态。
6. 状态术语不统一：桌面端使用“申请中／作业中”，App 综合列表使用“待审批／进行中”，分类列表又使用“申请中／作业中”。建议建立统一状态枚举和显示映射。
7. “作业单位”“作业所在单位”“申请单位”等组织字段需要明确主数据口径和 ID，而不能只保存名称。
8. 附件、地图点位、监控设备、关联作业票目前多为文本展示，正式实现应使用实体 ID 和关联表。
9. 当前无权限模型；正式系统至少应区分申请人、负责人、监护人、审批人、验收人和管理员。
10. 当前无数据持久化、接口错误、空态、加载态、离线、重复提交和并发审批处理。

## 七、建议的正式数据域

- `work_order`：作业票主表。
- `work_order_party`：参与单位和人员及其角色。
- `work_order_stage`：审批/实施/验收流程节点。
- `work_order_risk`：风险辨识项与评估结果。
- `work_order_measure`：安全措施及确认记录。
- `work_order_handover`：安全交底与签收。
- `work_order_monitor`：设备绑定与实时监测记录。
- `work_order_hazard`：过程隐患及整改闭环。
- `work_order_attachment`：方案、照片、签字等附件。
- `work_order_relation`：关联项目和关联作业票。
- `dictionary_work_type`、`dictionary_risk`、`dictionary_gas`：基础配置字典。
- `workflow_instance`、`workflow_task`：审批流程实例与待办任务。
